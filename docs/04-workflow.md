# 04 编排

编排定义整图以 **JSON 存在 MySQL**，以后加节点类型不必改表结构。

## 第一版跑什么

只执行一条链：**Start → 一个任务节点（跑 Handler）→ End**。

JSON 里可以先存更复杂的图，引擎遇到未实现的节点类型则失败或忽略（实现时选一种并写进测试），第一版不跑互斥/并行分支、汇聚、子流程、人工、循环。

任务节点走与普通 Task 相同的执行记录：插库、`PENDING → RUNNING` CAS、Handler、终态。流程在任务 **终态成功** 后进入 End，而不是 `submit` 时推进。

失败：任务节点 `FAILED` 则流程失败（第一版不做失败分支）。`RUNNING` 崩溃仍人工处理该任务行。

## 以后要加的（JSON 预留，引擎暂不认）

- 互斥分支、并行分叉/汇聚
- 子流程
- 延时节点（终态后 `ZADD` 到对应 slot）
- 条件边、节点级重试策略
- 人工节点、循环、扇出

## 与调度的关系

- 流程入口仍是一个可触发的 Task（Cron 等），到期后走 slot 锁 → 同步 ZADD 下次 → 异步建 **流程实例 + 任务节点的 Execution**。
- 入口 Task 的下次时间按普通 Trigger 写；流程内部推进不另占执行者编号。
- 下游若以后做延时节点，member 仍是配置/节点 ID，进 `hash % N` 对应 slot。
